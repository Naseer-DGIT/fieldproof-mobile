45 / 100.

The score is low because MobSF applies a generic Android scorecard that
penalizes any `exported=true` receiver, any Java `Random` usage in the
dependency tree, and any APK signed with a non-release keystore. Every

score is not a measure of the app's security posture.

## False positives explained

### Insecure RNG

Matches in obfuscated classes `l1/a.java`, `l1/b.java`, `l1/c.java`,
`m1/a.java`, `o/g.java`. These are AndroidX / plugin internals, not the
app's Dart code. Dart's `Random.secure()` compiles into `libapp.so` and
is not visible to jadx.

Verified:

Returns nothing. Only `Random.secure()` is used in the app.
`_generateRandomKey` in `key_store.dart` calls `Random.secure()`
internally; the identifier itself is not a use of an insecure RNG.

### Hardcoded secrets

Matched values are byte tables:

- `00 01 02 03 04 ...` — sequential byte table
- A bit-count table (0, 1, 1, 2, 1, 2, 2, 3, ...) in binary

These live in Bouncy Castle, JVM `Integer.bitCount` lookup tables, or
similar standard crypto/utility code. None are FieldProof secrets.

### Exported `ProfileInstallReceiver`

`android.permission.DUMP` has protection level `signature|privileged`.
Only the platform or system apps can send to it. A normal app cannot
reach it, regardless of `android:exported`.

### What this does not cover

- **Control flow.** `strings` reveals literals, not logic. Frida
  runtime hooks are required for that (S10).
- **Compiled constants.** Floats, integers, and short strings may be
  inlined into machine code and invisible to `strings`.
- **Encrypted blobs.** If the app embedded an encrypted payload, its
  plaintext is not visible; its ciphertext may be.



## What this does not cover

  runtime (S10).
- **Runtime behavior.** Static analysis sees the code; it does not see
  execution. S10.
- **Network behavior.** S6 covered the API. The mobile client's TLS
  behavior is S11.
- **iOS.** Only the Android APK was scanned.
